# LingoMatch 发布前界面复查

日期：2026-10-17。范围：当前本地项目；以 iPad 横竖屏为重点，兼顾小屏 iPhone 与多语言。此次仅新增审计材料，没有修改产品代码，没有上传新构建。

## 结论

已修复的 iPad 棋盘不是唯一需要适配的区域。其余主要界面能够显示，但存在一处应优先处理的小屏弹窗溢出，以及两种 Quiz 在 iPad 上大小失衡的问题。没有在本次已测试范围内确认 P0；这不等于所有功能、所有语言、所有真机已通过。

建议先修复本文第 1–3 项，再进行原生回归和重新打包。不能根据布局检查承诺 App Store 审核结果。

## 问题清单

### 1. P1：小屏德语无体力弹窗超出屏幕

**证据类型：真实组件布局验证 + 代码确认。**

触发条件：375×667、德语、无体力面板同时显示会员、广告、练口语、通知、广告不可用状态、复习与心情入口。测试使用实际组件有效属性组合，不是原生德语游戏中完成耗尽体力后复现。

卡片高约 747px，顶部 y≈-40；“Später spielen”按钮底部约 677px，超出 667px 视口。卡片没有内部滚动，公共模态逻辑又锁定页面滚动，因此不能依赖背景滚动找回内容。英语同尺寸卡片也偏高，但本次没有测到操作按钮越界；不能据此声称英语也无法退出。

代码：`src/components/mobile/DeadMachineSheet.tsx:85–107`，居中固定层、`max-w-[19rem]`，没有视口高度上限或滚动容器；`useModalDialog` 的页面滚动锁定。

证据：[截图](evidence/dead-de-375x667.png)、`batch-de-dead-recheck.log`。德语广告状态已改为本地化测试输入后复测，结果不变。

建议：卡片最大高度扣除 safe area 与上下边距；主体可滚动，退出动作保留可见；横屏一起回归。不要用缩小全部字体解决。

### 2. P2：iPad 选图 Quiz 仍是手机尺寸

**证据类型：真实组件布局验证 + UX 推断。**

1032×1376 中间题卡仅 352px 宽；左上说明、题卡、底部进度相距过远。屏幕能显示完整内容，但与刚放大的棋盘比例不一致，题目与图片显得过小。

代码：`src/index.css:6494` 的居中包装；`:6504` 的 `.candy-quiz-pick-card { max-width:22rem }`。

证据：[竖屏截图](evidence/quiz-pick-1032x1376.png)。

建议：平板使用约 560–640px 的自适应题卡，随可用高度收缩；题目、选项图、按钮同步调整。说明与进度围绕同一内容列组织，不改变手机布局。

### 3. P2：iPad 配对 Quiz 又过度拉伸

**证据类型：真实组件布局验证 + UX 推断。**

1376×1032 时配对区域约 1344px 宽，六行内容位于上部，下方留下大块空白；词语与图片横向距离过大。与选图 Quiz 呈现相反的尺度问题。

代码：`src/index.css:6382–6400`，`.candy-quiz-body` / `.candy-quiz-board` 的全宽、`flex:1` 扩展。

证据：[横屏截图](evidence/quiz-connect-1376x1032.png)。

建议：平板内容列约 800–900px 上限，行高与内容匹配；保留足够点击面积，但不把空白拉成整屏。选图与配对使用统一的平板信息框架。

### 4. P2：平板页面与弹窗的字体、内容尺度不统一

**证据类型：完整网页实际观察 + 组件布局 + UX 推断。**

Learned、Profile、收藏等页面已有居中内容宽度，但部分列表、说明、导航仍维持手机级小字。All Emojis 特别明显：宽面板中的词条文字、Emoji 较小，右侧留白较多。词条弹窗和结算卡则保留约 384px 宽。

代码：`src/index.css:6925` 附近平板页面约束；`src/components/mobile/LearnedWordModal.tsx:59` 的 `max-w-sm`；`src/index.css:6221` 附近结算卡上限。

证据：[词典实际页面](evidence/actual-dictionary-ipad.png)、[已学实际页面](evidence/actual-learned-ipad.png)、[词条实际页面](evidence/actual-word-ipad.png)。

建议：建立少量平板尺寸档位（简短确认、内容弹窗、完整玩法），不要所有弹窗一律放到 800px。优先调整玩法与高频词条的可读性，再统一次要说明和导航。当前 Profile 等界面大体能容纳内容，不需要全部重做。

### 5. P2：Learned 教学弹窗未封闭键盘焦点

**证据类型：浏览器实际键盘操作 + 代码确认；不是 VoiceOver 真机测试。**

教学显示时连续 Tab，焦点依次进入背景的 Review、All、Reinforce、Fortified，而不是留在弹窗内；四次记录均为 `insideDialog:false`。外接键盘/辅助操作可能落到遮罩后。

代码：`src/components/mobile/LearnedPanel.tsx:311–324`，有 `role="dialog"`，但未使用其他弹窗使用的 `useModalDialog`。

建议：接入共享模态焦点管理，初始焦点落到 Skip 或 Next；限制焦点在弹窗内，关闭后还原焦点，背景不可交互。

补充：本轮已通过鼠标拖动模拟横向手势，从第一页切到“Memory shields”。**没有复现之前“完全不能左右滑”的问题**，不要重复修复历史状态。

## 仍需验证：键盘打开后旋转

原生第一次测试中，竖屏已打开登录键盘后旋转到横屏，观察到输入框/提交区域在键盘之下；该截图同时存在旋转过渡的裁切/黑边，不能当作稳定最终布局的充分证据。

独立复测“直接以横屏打开登录”成功，输入框与提交区域出现在键盘上方。另一次尝试延长旋转等待的测试，因为模拟器键盘未出现，在进入旋转检查前就失败；这属于测试限制，不能算产品失败，也不能算复测通过。

证据：`native-1.log`、`native-direct-landscape.log`、`native-repeat-limitation.log`；[首次旋转截图](evidence/native-signin-keyboard-landscape.png)、[直接横屏截图](evidence/native-signin-direct-landscape.png)。

建议：真机/受控模拟器执行“竖屏登录→打开键盘→横屏→等待稳定→滚动→返回竖屏”，确认后再定级或修复。不能笼统说“横屏登录坏了”。

## 本轮未发现明显布局阻断的区域

在所测尺寸和样例内，课程、隐私、通知设置、登录/注册静态表单、模式/分类、会员/试用、成就/奖励、法律说明、Say & Blast 介绍等均能挂载和呈现；除上述无体力情况，布局测量未报告其他无可滚动祖先的越界按钮。

这只是样例布局结果，不等于点击回调、原生 SDK、数据恢复、课程内容和付费逻辑都已经通过。也没有发现就自动判定“页面美观/无需优化”。

## 建议实施顺序（待确认，不自动执行）

1. 无体力弹窗限制高度、主体滚动、退出可达；回归所有有效入口组合与长文本。
2. 一起调整 iPad 选图/配对 Quiz 的内容宽度、字号、间距与横屏比例。
3. 补齐 Learned 教学的焦点管理；保留已有效的左右滑动。
4. 统一高频平板词条/列表尺度，避免一次重做全 App。
5. 原生复测键盘旋转、所有修改页面横竖屏及 iPhone 回归，再重新打包、同步 Xcode；使用实际 iPad 界面制作商店截图。

正式广告、通知送达、支付/恢复、麦克风识别、离线/中断恢复以及已上传构建的一致性仍属于独立发布验证项。本报告不替代这些测试。
